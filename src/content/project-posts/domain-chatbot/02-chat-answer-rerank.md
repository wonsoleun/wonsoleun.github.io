## - A. 답변 출력: 목록 → 채팅, 수식·그림 표시


### 문제 인식

**핵심 문제**
1. 답변이 Top-k 후보 카드 5개로 나옴 → 사용자가 직접 골라야 함
2. 그림이 답변에 나오지 않음
3. 수식이 수식이 아니라 글자로 찍힘 (`\frac{L}{100}` 이 그대로 보임)

<br>

**원인 분석**

코드를 보니 세 문제 모두 검색이 아니라 화면(`static/index.html`) 쪽 문제였다.

| 증상 | 원인 |
| --- | --- |
| 후보 목록 | 화면이 검색 결과 `k`개를 전부 카드로 그리게 되어 있음 |
| 그림 없음 | 그림은 카드를 눌러야 열리는 오른쪽 패널에만 들어 있음 |
| 수식이 글자 | (1) KaTeX가 `$$ … $$` 만, 그것도 인라인으로 처리 <br> (2) LLaMA 답변은 `esc()` 후 글자 그대로 출력 |

수식 문제를 조금 더 보면,

- chunk 본문의 수식은 `$$ … $$` 로 저장되어 있어서 KaTeX가 처리함
- 그런데 LLaMA는 수식을 `\[ … \]`, `\( … \)`, `$ … $` 로도 씀 → 구분자가 등록되어 있지 않아 글자로 남음
- LLaMA 답변의 Markdown(`**굵게**`, 목록)도 변환 없이 그대로 찍힘

<br>

---

### 해결 과정

**1. 1위 조항 하나로 답하기**

- 화면이 `k: 1` 로 요청 → 후보 카드와 결과 수 선택 제거
- 답변 구성: 조항 원문(또는 LLaMA 답변) → 그림 → 표 → 출처
- 출처를 누르면 오른쪽 패널에 조항 전문

<br>

**2. 수식 구분자 등록**

| 구분자 | 표시 |
| --- | --- |
| `$$ … $$`, `\[ … \]` | 블록 수식 (가운데 정렬) |
| `\( … \)`, `$ … $` | 인라인 수식 |

<br>

**3. Markdown 변환 전에 수식을 먼저 빼 두기**

- Markdown 변환기는 `_` 를 기울임, `\` 를 이스케이프로 해석함
-> `L_{LL}` 같은 LaTeX가 변환 과정에서 깨짐 <br>
-> 수식 구간을 먼저 자리표시자로 바꾸고, 변환이 끝난 뒤 되돌려 넣자 <br>

```text
render_answer(text):
    math = []
    text = 수식 구간($$..$$, \[..\], \(..\), $..$)을 @@MATH0@@ 같은 자리표시자로 바꾸고 math에 보관
    html = sanitize(markdown_to_html(text))     # marked + DOMPurify
    html = 자리표시자를 원래 수식으로 복원
    KaTeX(html)                                 # 구분자에 따라 블록 / 인라인
```

<br>

**4. LLaMA 지시문 추가**

논문의 지시문 3개 뒤에 4번을 추가했다. (논문과 다른 점)

> Write every equation in LaTeX exactly as given in the rule, on its own line between $$ and $$. Never rewrite an equation as plain text.

-> 화면에서 고쳐도 LLaMA가 수식을 `t = 5.5 + 0.02L` 처럼 평문으로 쓰면 소용이 없기 때문

<br>

**결과**

- 수치로 잰 항목은 아님. 가짜 검색 결과를 넣은 렌더링 테스트와 실제 화면으로 확인
- 블록 수식, 인라인 수식, 굵은 글씨, 목록이 답변 안에서 렌더링됨
- LLaMA 답변에 섞인 `<img onerror=…>` 같은 태그는 DOMPurify가 제거

<br>

**남은 것**

- 표 셀 안의 수식은 여전히 글자 (변환 단계에서 LaTeX로 바뀌지 않음)
- LLaMA가 수식을 틀리게 옮길 수 있음 → 출처의 원문 수식과 비교 필요


<br>

## - B. 재정렬: 정답을 찾아 놓고도 1위가 아닌 문제


### 문제 인식

A에서 1위 하나로만 답하게 바꾸자, "1위가 정답인 비율"이 곧 챗봇 정확도가 됐다.
<br> → 직접 만든 60문항(Pt.2 18, Pt.3 18, Pt.5 24)으로 측정

| | Top-1 | Top-5 |
|:---|:---:|:---:|
| base | 0.75 | 0.97 |
| adapted | 0.82 | 0.97 |

(임베딩 텍스트에 제목 경로를 붙인 뒤의 값)

<br>

**핵심 문제**
1. 정답은 거의 다 5위 안에 있는데(0.97), 1위는 0.75~0.82
2. 틀린 문항 대부분이 "정답이 2~5위"인 경우 → 못 찾은 게 아니라 순서가 틀린 것
3. 1위로 잘못 올라오는 것은 주로 바로 옆 조항

| 정답 | 1위로 올라온 조항 |
| --- | --- |
| Pt.3 Ch.12 Sec.2 [3.4] (주 잠금 장치) | Pt.3 Ch.12 Sec.2 [3.6] (보조 잠금 장치) |
| Pt.5 Ch.1 Sec.3 [2.2] | Pt.5 Ch.1 Sec.3 [2.4] |

<br>

**원인 분석**

1. bi-encoder는 질문과 조항을 **따로** 임베딩한 뒤 dot product로 비교한다.
2. 조항 1만여 개를 미리 임베딩해 둘 수 있어서 빠르지만, 조항 전체를 벡터 하나로 압축한다.
3. 같은 Section의 옆 조항은 단어와 문장 구조가 거의 같아서 벡터도 가깝다 → 미세한 차이가 순위에 반영되지 않음

<br>

---

### 해결 과정

**방향**

- cross-encoder는 질문과 조항을 **함께** 읽고 점수를 낸다 → 더 정밀함
- 대신 미리 계산해 둘 수 없어서 전체 DB(11,574개)에 쓰기에는 너무 느림
-> 빠른 모델로 후보를 뽑고, 정밀한 모델로 순서만 다시 매기자 (retrieve & re-rank)

<br>

```text
search(query, k):
    cands  = bi_encoder_top_n(query, n=10)                         # 미리 임베딩된 인덱스, dot product
    scores = [cross_encoder(query, embed_text(c)) for c in cands]  # 제목 경로·표 포함 텍스트
    return sort(cands, by=scores)[:k]
```

- 재정렬 모델: `cross-encoder/ms-marco-MiniLM-L-6-v2` (GPL 라벨링에 이미 쓰던 모델)
- 입력 텍스트는 인덱스와 같은 것(제목 경로 + 본문 + 참조 표 평문)
- 인덱스와 학습은 그대로 → `config.yaml` 의 `retriever.rerank.top_n` 으로 켜고 끔
- 평가 스크립트가 재정렬 전(`base`)과 후(`base+rr`)를 나란히 출력하도록 수정

<br>

**결과** (60문항)

| | Top-1 | 고친 문항 | 망친 문항 |
|:---|:---:|:---:|:---:|
| base → base + 재정렬 | 0.75 → 0.85 | 9 | 3 |
| adapted → adapted + 재정렬 | 0.82 → 0.85 | 5 | 3 |

→ 위 예시의 `[3.4]` / `[3.6]` 문항은 재정렬 후 정답이 1위로 올라옴

→ 재정렬을 켜면 base와 adapted의 결과가 같아짐 (60문항 중 59문항의 1위가 동일)

<br>

**남은 것**

- 남은 오답 9문항 중 7문항이 Pt.2 (Pt.2 Top-1 0.61)
- 재정렬이 망친 3문항도 전부 Pt.2
-> "steel castings" 질문에 주강품 `Sec.8 [5.3]` 대신 단강품 `Sec.6 [7.3.1]` 을 1위로 올림 <br>
-> 일반 웹 검색 데이터로 학습한 재정렬 모델은 문장이 거의 같은 조항을 가리지 못함 <br>
- 60문항에서는 오차가 ±11%p 정도 → 6문항 차이는 방향만 확인한 수준. 새 질문으로 다시 확인 필요
